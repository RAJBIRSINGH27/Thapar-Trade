% 1 HIGHER-ORDER GOAL

\section{Higher-order goal}

This project provides Thapar students with a centralized, structured
and campus-focused marketplace for buying, selling and exchanging
products within the student community. The prototype connects
authenticated users, product listing management, marketplace
discovery, search and filtering, listing status management, reporting,
and administrative moderation into a single web platform.

The wider goal is to replace fragmented informal channels such as
WhatsApp groups, social media, personal contacts and scattered
messages with a dedicated marketplace that improves discoverability,
organization and trust.

\section{Problem Statement}

Student-to-student buying and selling at Thapar is commonly conducted
through informal channels such as WhatsApp groups, social media,
personal contacts and word of mouth. These channels are convenient
but do not provide a structured marketplace workflow.

Common pain points include:

\begin{itemize}

    \item \textbf{Scattered listings:} products are distributed
    across multiple groups, chats and personal networks.

    \item \textbf{Poor discoverability:} useful listings can
    disappear quickly among unrelated messages, making relevant
    products difficult to locate.

    \item \textbf{Limited search and filtering:} buyers cannot
    consistently search products by category, price, condition or
    availability.

    \item \textbf{Stale availability:} sellers may not update or
    remove listings after an item has been sold.

    \item \textbf{Trust concerns:} buyers need confidence in the
    seller and the information provided about a product.

    \item \textbf{Lack of moderation:} there is no centralized
    campus-specific mechanism for reporting and reviewing
    misleading, unauthorized or problematic listings.

\end{itemize}

\textbf{Why this matters now:}
students need a single, searchable and organized platform through
which they can discover products, publish listings, communicate with
other students and maintain accurate availability information.

\section{Solution Approach}

This is an engineering course project, so the emphasis is on a
working, testable campus marketplace rather than novel algorithm
research. The solution is divided into independently understandable
functional modules.

\subsection{Marketplace and listing engine}

The listing workflow is structured around product information and
availability.

A seller provides the product title, category, description, price,
condition and images. The system stores the listing and exposes it
through the marketplace. The seller can subsequently edit, delete or
update the status of the listing.

The principal listing states are:

\begin{center}
\textbf{AVAILABLE \quad $\rightarrow$ \quad RESERVED \quad $\rightarrow$ \quad SOLD}
\end{center}

This explicit lifecycle reduces stale availability and provides
buyers with clearer information about the current state of an item.

\subsection{Web architecture}

A 3-tier web architecture is used:

\begin{itemize}

    \item \textbf{Frontend:}
    React.js and Tailwind CSS provide the responsive marketplace,
    listing interfaces, search and filtering, user profile
    functionality and administrative views.

    \item \textbf{Backend API:}
    Node.js and Express.js provide the application services and
    REST-style communication between the frontend and the data
    layer.

    \item \textbf{Database:}
    MongoDB provides persistent storage for users, listings and
    marketplace records.

\end{itemize}

The documented technology stack additionally includes JWT for
authentication, AWS S3 for image storage and Razorpay for
payment-related marketplace functionality.

\subsection{Listing and moderation status}

The marketplace separates normal student operations from
administrative moderation.

A student can report a listing that appears misleading,
unauthorized or otherwise problematic. The report is stored and made
available to the administrator for review.

The administrator can inspect the report and take an appropriate
action, including removing or restoring the listing.

% 6 EVALUATION CRITERION
% ================================================================
\section{Evaluation Criterion}

\subsection{Primary evaluation metric}

\textbf{Listing-to-discovery efficiency (LDE):}
time required for a user to locate a specified relevant product using
the marketplace search and filtering functionality.

\begin{itemize}

    \item \textbf{Target:} the majority of pilot users should be able
    to locate a specified listing within a short predefined task
    window.

    \item \textbf{Attribution:} task completion time can be recorded
    during user-acceptance testing.

\end{itemize}

\subsection{Secondary evaluation metrics}

\begin{itemize}

    \item \textbf{Listing completion rate:}
    percentage of users who successfully publish a valid listing.

    \item \textbf{Search success rate:}
    percentage of users who successfully find the intended item
    during predefined search tasks.

    \item \textbf{Usability:}
    average user rating of navigation, marketplace browsing and
    listing creation on a 1--5 scale.

    \item \textbf{Listing freshness:}
    percentage of sampled listings whose Available, Reserved or Sold
    state correctly reflects their current status.

    \item \textbf{Reliability:}
    successful execution of authentication, listing creation,
    search, update and reporting operations.

    \item \textbf{Performance:}
    response time of common marketplace and listing operations under
    expected student workload.

\end{itemize}

\subsection{Pilot validation plan}

\begin{itemize}

    \item Recruit a small group of student users representing both
    buyers and sellers.

    \item Provide predefined tasks such as finding a product below a
    specified price or creating a listing for a used item.

    \item Record task completion, errors, time taken and user
    feedback.

    \item Use the results to refine the marketplace interface and
    workflow before the final demonstration.

\end{itemize}

% 7 SCALABILITY
% ================================================================
\section{Scalability}

\begin{enumerate}

    \item \textbf{Scalable architecture:}
    the frontend, backend and database responsibilities are separated,
    allowing individual components to evolve independently as the
    number of users and listings increases.

    \item \textbf{Marketplace growth:}
    database indexing, pagination and efficient search queries can
    support increasing numbers of listings.

    \item \textbf{Image scalability:}
    product images can be stored separately from core transactional
    data using cloud object storage such as AWS S3.

    \item \textbf{Modular deployment:}
    the application can be deployed on common web-hosting
    infrastructure and migrated to larger infrastructure as usage
    grows.

\end{enumerate}

\section{Engine availability heuristic}

The prototype uses mature and commonly available web-development
technologies rather than requiring novel infrastructure.

React.js and Tailwind CSS provide the frontend, while Node.js and
Express.js provide the backend API. MongoDB provides persistent
application data storage. JWT provides authenticated access, while
GitHub is used for version control and team collaboration.

The documented technology stack also includes AWS S3 for image
storage and Razorpay for payment-related functionality.

This technology combination allows the team to focus on marketplace
workflow, usability, listing management and moderation rather than
building infrastructure from scratch.

% ================================================================
% 10 RISKS AND MITIGATIONS
% ================================================================
\section{Risks and mitigations}

\begin{itemize}

    \item \textbf{Misleading listings:}
    provide reporting reasons and an administrative review workflow
    so problematic listings can be investigated.

    \item \textbf{Stale availability:}
    use explicit Available, Reserved and Sold states and allow
    sellers to update listing status.

    \item \textbf{Incomplete listings:}
    validate required product information before allowing a listing
    to be published.

    \item \textbf{Trust concerns:}
    restrict marketplace functionality to authenticated users and
    provide reporting and moderation mechanisms.

    \item \textbf{Integration defects:}
    perform feature-level tests followed by integrated testing across
    the frontend, backend and database.

    \item \textbf{Limited development resources:}
    prioritize the complete core marketplace before advanced
    functionality such as notifications, analytics and additional
    communication features.

\end{itemize}

\section{Summary}

The ThaparTrade prototype delivers a centralized campus marketplace
for student-to-student buying and selling. It provides authentication,
listing creation and management, marketplace browsing, search and
filtering, listing status management, user profiles, reporting and
administrative moderation.

The project addresses the fragmentation of informal student trading
channels by providing a structured workflow for publishing and
discovering products. The separation of frontend, backend and
database responsibilities provides a foundation for future
scalability and additional marketplace functionality.

The next iteration can focus on deeper user testing, improved
marketplace discovery, enhanced moderation, notifications,
buyer-seller communication and other extensions while retaining the
core marketplace workflow.
